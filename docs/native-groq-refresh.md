# Native Groq setup and messenger demo

The Android reference is `AddKeyStep.kt` and `SettingsScreens.kt`: onboarding contains an expanded Groq key form, while Settings offers all providers. Android currently explains the other-provider route in a dialog before continuing its checklist. The owner explicitly requested direct Settings navigation for the native apps, so Windows, macOS, iPhone and iPad open API Keys, then continue the remaining OS setup. Adding a key can wait until afterward; dictation remains gated on a configured provider. Drafts survive returning to the Groq page. The physical Android phone was disconnected during this pass; source and retained Settings screenshots were inspected.

Windows 2.0.4 is installed at `%LOCALAPPDATA%\Programs\Quill\Quill.exe`, with a Start shortcut and per-user uninstall registration. Its separate data directory survives updates. The original Gemini and OpenRouter DPAPI files and legacy settings were backed up and verified byte-identical after installation. A previously missing settings migration now preserves the selected provider/model, Alt + E shortcut, appearance, cleanup preference and other supported settings without overwriting existing native preferences or granting native insertion consent.

The messenger illustration uses Android's existing video conversation verbatim: “hello”, “when will i get my delivery?”, and “You will get it by tomorrow at 12 noon latest. Thanks for your patience.” It loops through shortcut/control activation, recording, transcription and insertion, with a persistent editing caret. Desktop versions also show a pointer and use their registered shortcut; iOS and iPadOS use the Quill keyboard control. Native rendering adapts to both appearances and reduced motion. The illustration performs no recording, input injection or network requests.

Consistency fixes include displaying the actual registered Windows shortcut, explaining fallback separately, moving incomplete setup above the practice field, keeping setup navigation accurate at narrow widths, and showing a nonactivating recording indicator while a desktop session is active even when its idle floating control is hidden. Writing-style overrides retain case-insensitive app matching after restart, and old dictation errors clear without hiding unrelated notices. A 503 has specific temporary-provider-failure copy. The existing bounded Gemini retries, cleanup deadline and raw-transcript fallback remain; no provider or model is switched silently.

The installation audit also found a stale sign-in command pointing to an old development executable, despite the saved startup preference being enabled. Installer follow-up `5740a4b` repairs an existing Quill startup command to the installed executable, preserves absent/unrelated commands, and removes only its own exact startup command on uninstall. Its isolated-runner regressions passed on both architectures. The repaired package is installed, and the current sign-in command now points to `%LOCALAPPDATA%\Programs\Quill\Quill.exe --background`.

Provider capacity is outside the app's control. Google's [troubleshooting guide](https://ai.google.dev/gemini-api/docs/troubleshooting) recommends exponential backoff for transient failures. Groq's [rate-limit documentation](https://console.groq.com/docs/rate-limits) distinguishes rate limits and `Retry-After`. Provider-directed retry timing and an explicitly chosen fallback are useful future improvements; automatic quota/authentication retries or undisclosed provider switching would be poor defaults.

## Readiness judgment

Windows has the strongest local installation evidence and is a daily-use beta candidate, subject to the still-pending installed microphone-to-insertion acceptance check. The installed executable reports `NotSigned` in Authenticode inspection; public distribution signing is still a release gate. macOS has a coherent native interface and strong runner coverage, but distribution signing/notarization and physical-device acceptance remain release gates. iPhone/iPad now have an integrated keyboard-session flow and passing installed-extension checks; physical microphone, interruptions, Bluetooth and sustained background sessions still need device acceptance before public release. None of the three should be described as fully release-ready solely from CI.
